ERC-1967 · UUPS · delegatecall

代理合约图解

从一次 bid() 调用出发，看清代理、实现合约和存储之间到底发生了什么。所有数字来自本地 Hardhat 节点的一次真实部署。

琥珀：实现地址（便利贴） 蓝色：代码 青色：存储

00 / 先建立一个比喻

代理就是公司前台

客户只认「1 楼前台」这个地址。前台自己不办业务，桌上有一张便利贴，写着业务部现在在哪个房间。客户来了，前台照着便利贴把人和资料带过去。

这个比喻里的四个东西，和代码里一一对应：前台 = 代理合约（地址不变）；便利贴 = 0x3608… 存储槽；房间号 = 实现合约地址；换房间 = 升级。

01 / 部署

地址是怎么被写进便利贴的

代理不是「认识」NFTAuctionMarket 这个名字，它只认识一个 20 字节的地址。这个地址是部署时作为构造参数传进去的。

STEP 1

先部署实现合约

得到地址 0x9fE4…a6e0。这份合约自己也有存储，但以后没人会用它，它只提供代码。

STEP 2

再部署代理

new NFTAuctionMarketProxy(0x9fE4…, initData)。代理源码里只看到 address implementation，看不到合约名。

STEP 3

构造函数写槽并初始化

父合约 ERC1967Proxy 把地址写进固定槽，然后 delegatecall 一次 initialize()，把 owner 等初始值写进代理存储。

地址是显式传入的：三段代码接起来看

你可能觉得「代理源码里没提 NFTAuctionMarket，怎么算显式」。其实地址一直在传，只是分了三层：

① ignition 部署脚本 
const impl =
  m.contract("NFTAuctionMarket");
// 先拿到实现合约地址

const proxy = m.contract(
  "NFTAuctionMarketProxy",
  [impl, initializeData]  // ← 传入
);
② 你的代理合约 
constructor(
  address implementation,
  bytes memory data
)
  ERC1967Proxy(implementation, data)
  payable {}
// 收到的地址原样交给父合约
③ OZ 父合约 
constructor(
  address implementation,
  bytes memory _data
) payable {
  ...
  ERC1967Utils.upgradeToAndCall(
    implementation, _data);
}
// 内部 _setImplementation()
// slot 0x3608… = 地址
代理字节码
代理合约本身的代码
参数 1
implementation = 0x9fE4…
参数 2
initialize 的 calldata

一笔合约创建交易 = 字节码 + ABI 编码后的构造参数。在 Etherscan 的创建交易里展开 “Constructor Arguments”，就能直接看到这个地址。

部署完成后，读代理的 0x3608…bbc 槽，真实值是：
0x0000000000000000000000009fe46736679d2d9a65f0992f2272de9f3c7fa6e0

高亮的那 20 字节就是实现合约地址。实现合约自己的这个槽是空的：0x0000…0000，因为它不是代理。

为什么源码里不需要 import？ 因为 address 只是一个数字类型。快递单上写「XX 路 301」，快递员不需要认识那栋楼里的人。代理运行时要的是地址，不是合约类型。

02 / 调用

一次 bid() 的五步旅程

点「下一步」逐步看。左侧是流程，右侧是每一步在代码里对应什么。

第 1 / 5 步
用户调用 bid()

用户在钱包里点「出价」。交易的目标地址是代理 P，不是实现合约。用户永远只跟代理打交道。

第 2 步的底层细节：Solidity 编译后的字节码开头是一段分发器，拿 msg.sig（calldata 前 4 字节）逐个和函数选择器比对。代理的 ABI 里只有构造器和 fallback，所以任何业务调用都匹配不上，必然掉进 fallback。

03 / 核心机制

delegatecall 到底共享什么

这是理解代理的唯一门槛。一句话：代码从实现合约借来执行，但所有的身份和记忆都留在代理身上。

维度calldelegatecall
执行谁的代码被调用合约被调用合约
用谁的存储被调用合约调用者（代理）
msg.sender当前合约原始用户
msg.value可以重新指定原样保留
address(this)被调用合约代理地址
合约余额被调用合约代理地址

04 / 升级

升级只改便利贴上的号码

升级只改便利贴上的号码。先搞清楚是谁把号码改掉的，再自己动手。

代理里没有修改地址的源码，那是谁改的？

你的 NFTAuctionMarketProxy.sol 里确实没有任何升级函数。改地址的代码住在实现合约里，通过 delegatecall 执行，所以写进去的是代理的存储。

实现合约继承了什么 
// NFTAuctionMarket.sol:13
contract NFTAuctionMarket is
  Initializable,
  UUPSUpgradeable,
  OwnableUpgradeable
// ↑ 来自 UUPSUpgradeable
升级函数（OZ 提供） 
function upgradeToAndCall(
  address newImpl, bytes memory data
) public payable virtual onlyProxy {
  _authorizeUpgrade(newImpl);
  // 你的实现：onlyOwner
  _upgradeToAndCallUUPS(newImpl, data);
}
真正写槽的一行 
// ERC1967Utils
_setImplementation(newImpl);

// 内部等价于：
// StorageSlot.getAddressSlot(
//   0x3608…).value = newImpl;

// 一条 SSTORE 指令

关键：_setImplementation 里是一条 SSTORE 指令。因为整段代码是通过 delegatecall 执行的，EVM 把这条指令作用在代理的存储上，而不是实现合约自己的存储。所以代理的代码一行没改，但它存的那格地址变了。

点一下按钮，看代理指向从 V1 换成 V2。注意右侧存储表格：一个字节都不会变。

为什么升级不会丢数据？V1 和 V2 读的是同一批存储槽。V2 只是在 V1 的变量后面追加了 highValueFeeBps 和 highValueThreshold，老格子的含义完全没动。三条铁律：只追加、不删除、不改类型和顺序。

05 / 升级之后

旧的函数或数据出错了怎么办

先把问题分成几类，处理方式完全不同。核心认知：升级换的是代码来源，不会自动修数据。

A · 单笔调用

某一笔交易 revert

比如加价不到 5%，触发 BidTooLow。

整笔回滚，存储不变。用户加价重试即可。EVM 交易是原子的，不存在改一半。

B · 代码 bug

新版逻辑写错了

V2 的某个函数有漏洞。

再部署 V3，owner 再调一次 upgradeToAndCall。注意：升级是整份实现一起换，不能只换一个函数。

C · 数据不兼容

老数据读出来是乱的

V2 改了老变量的类型或顺序，旧值被错误解释。

升级修不了存储。只能在新版本里写 migrate()，把老数据逐条转换成新格式。

D · 升级失败

initializeV2 回滚

升级交易里的初始化步骤失败。

地址修改和初始化在同一笔交易里，会一起回滚。代理仍然指向旧实现，系统不受影响。

E · 接口变化

函数被删掉或改名

老前端发来的选择器在新实现里不存在，直接 revert。

保留旧函数签名，内部转调新函数；或者同步更新前端 ABI。

F · 最坏情况

升级函数本身被弄坏

新实现删掉了 upgradeToAndCall，或改坏了权限检查。

如果 owner 也无法再升级，合约就永久锁死。所以升级前必须测试，并保护好 owner 私钥。

回滚也是一次升级：把便利贴改回 V1 的地址。通常 V1 不读 V2 新增的变量，所以是安全的；但如果 V2 改过老数据的含义，回滚也会读到坏数据，仍然需要迁移。

06 / 自测

三个问题，检验有没有真的懂

先在心里回答，再点开。

代理合约里为什么找不到 bid() 的代码？

因为代理不需要包含业务代码。它只需要在运行时从固定槽里读出一个地址，然后用 delegatecall 把原始 calldata 原封不动转发过去。代码由实现合约提供，存储和身份留在代理。

升级到 V2 之后，升级前创建的拍卖数据会丢吗？

不会。数据一直在代理的存储里，V2 只是换了一份代码来读同一批槽。前提是 V2 严格只追加新变量，没有改动老变量的顺序、类型或含义。

当前最高出价者能调用 WithdrawRefund 把钱拿回去吗？

不能。被记进 pendingReturns 的是「刚刚被顶掉的上一位出价者」，当前最高出价者的余额是 0，调用会被 NothingToRefund 拦住。这就是 pull-over-push 退款模式。

07 / 记住这几句

一页纸总结

地址在代理，代码在实现；
数据在代理，权限在代理；
升级只改便利贴。

部署写槽 + delegatecall initialize
调用fallback → 读槽 → delegatecall
升级实现里的代码改写代理的槽 + 初始化
回滚再升级一次，指回旧地址

如果只能记住一件事：用户永远只跟代理地址交互；实现合约的地址只是一个可以更换的配置项。
